# Thailand Regional Banking Intelligence

ระบบวิเคราะห์ตลาดธนาคารพาณิชย์รายจังหวัดจากข้อมูลสาธารณะจริง ประกอบด้วย PostgreSQL warehouse, ETL ที่จัดตารางด้วย Airflow, เว็บ Next.js, Grafana และผู้ช่วยวิเคราะห์ที่เลือกผู้ให้บริการ LLM ได้

สนับสนุนการวิเคราะห์ตลาดของทีมกลยุทธ์และการวางแผนช่องทาง ด้วยข้อมูลที่ตรวจสอบสูตรและแหล่งที่มาได้

## ปัญหาธุรกิจ

ยอดสินเชื่อรวมเพียงอย่างเดียวทำให้กรุงเทพฯ เด่นกว่าจังหวัดอื่น ขณะที่แต่ละจังหวัดมีประชากร ขนาดเศรษฐกิจ และเครือข่ายสาขาต่างกัน ข้อมูลที่ใช้เปรียบเทียบมาจากหลายหน่วยงาน ซึ่งมีชื่อจังหวัด หน่วย ความถี่ และเวลาประกาศไม่ตรงกัน

ระบบเชื่อมข้อมูลสาธารณะ 5 ชุดจาก 4 หน่วยงาน เข้าสู่ตารางวิเคราะห์ระดับจังหวัด–เดือน เพื่อเปรียบเทียบขนาดตลาด การเติบโต และตัวชี้วัดต่อประชากร/ต่อสาขา พร้อมตรวจสูตรและที่มาได้ รายชื่อที่ผ่านเกณฑ์คัดกรองใช้เลือกพื้นที่สำหรับศึกษาเพิ่มเติม การประเมินความต้องการบริการหรือกำไรต้องใช้หลักฐานประกอบเพิ่มเติม

## สิ่งที่ใช้งานได้

| ส่วน | ความสามารถ |
| --- | --- |
| ภาพรวมตลาด | สินเชื่อ เงินฝาก สาขา YoY แนวโน้ม และการกระจุกตัว |
| วิเคราะห์จังหวัด | ประวัติรายจังหวัด เปรียบเทียบสูงสุด 4 จังหวัด GPP และเกณฑ์คัดพื้นที่ |
| ผู้ช่วยวิเคราะห์ | ถามภาษาไทย จัดอันดับด้วย metric ที่ชัดเจน กรองข้อมูล เปรียบเทียบ ดู YoY และถามต่อ |
| บทสนทนา | แนะนำความสามารถ อธิบายนิยามผลล่าสุด และเปลี่ยนกราฟ/ตารางจากผลเดิม |
| คำถามธุรกิจ | 10 คำถาม พร้อมผลจริง SQL พารามิเตอร์ และข้อควรระวัง |
| แหล่งข้อมูล | Coverage ปีอ้างอิง เวลาดึง กฎ availability และสถานะ ETL ที่ตัดรายละเอียดภายใน |

รองรับ Groq, Gemini และ OpenAI โดยเลือก provider ชัดเจนและไม่สลับไปเรียก provider อื่นอัตโนมัติ ผลตรวจ Live ล่าสุดใช้ Groq กับ `openai/gpt-oss-20b` คำถามวิเคราะห์ใช้ hybrid planner: กฎสำหรับคำที่รู้จักและ LLM สำหรับสำนวนที่ยังแปลไม่ได้ ทุกแผนต้องผ่าน Pydantic และ Semantic validation ก่อนสร้าง SQL แบบ read-only ฝั่ง Groq ใช้ JSON Object Mode พร้อมตรวจ schema ภายในระบบ ไม่ใช่การรับประกัน strict decoding หากไม่มีคีย์ ยังดู dashboard และวิเคราะห์แบบกฎได้ โดยการตีความบทสนทนาจะจำกัดกว่า

## ข้อมูลและเทคโนโลยี

Snapshot ที่ตรวจ: **77 จังหวัด × 25 เดือน = 1,925 แถว** ตั้งแต่ **กรกฎาคม 2567–กรกฎาคม 2569** ไม่ใช่การรับรองว่าข้อมูลต้นทางล่าสุด ณ ทุกวันที่เปิดอ่าน

- ธปท. FI_CB_011_S5: ตารางเว็บทางการ สำหรับสินเชื่อ เงินฝาก และสาขารายเดือน
- กรมการปกครอง: TXT ทางการ สำหรับประชากรทะเบียนรายปี
- สศช.: Workbook สำหรับ GPP รายจังหวัด
- World Bank: JSON REST API สำหรับเงินเฟ้อไทยรายปี โหลดต้นทางแล้ว แต่ snapshot นี้ยังใช้ประกอบงวดธนาคารย้อนหลังไม่ได้ตามเงื่อนไขวันเผยแพร่
- ธปท. MPC: Workbook มติอัตราดอกเบี้ยนโยบาย ไม่ใช่ BOT Policy Rate REST API

อ่าน [แหล่งข้อมูล หน่วย mapping และ temporal joins](docs/data-sources.md)

Stack หลัก: Next.js + TypeScript + Recharts, Python + FastAPI, PostgreSQL, Airflow, Grafana, LangChain + LangGraph, Pydantic และ SQLGlot ดู [สถาปัตยกรรมและ data model](docs/architecture.md)

## เริ่มใช้งาน

ติดตั้ง Docker Desktop ที่ใช้ Linux containers แล้วรันจาก root ของ repository ใน PowerShell:

```powershell
docker compose up -d --build postgres api web
docker compose exec api python -m bank.etl all
```

การโหลดครั้งแรกต้องใช้อินเทอร์เน็ตและอาจใช้เวลาหลายนาที ตรวจว่าทุกขั้นสำเร็จก่อนใช้งาน เปิด [เว็บแอป](http://127.0.0.1:3000) หรือ [API docs](http://127.0.0.1:8000/docs)

รายละเอียดการตั้งค่า LLM provider, เปิด Grafana/Airflow, พัฒนา และแก้ปัญหาอยู่ใน [คู่มือเริ่มต้น](docs/getting-started.md) การโหลดข้อมูลและดู dashboard ไม่ต้องใช้คีย์ LLM เก็บคีย์ไว้ใน `.env` ส่วนตัว ห้ามใช้ตัวแปร `NEXT_PUBLIC_*` กับ secrets

## ผลตรวจ

ผลตรวจล่าสุดที่บันทึก: **24 ตุลาคม 2569 (Asia/Bangkok)**

| การตรวจ | ผล | ขอบเขตหลักฐาน |
| --- | --- | --- |
| Python regression | 212 tests ผ่าน | Analytics บนฐานข้อมูลจริง และ provider tests แบบ deterministic/mock |
| คำถามวิเคราะห์ภาษาไทย | Offline 80 ข้อผ่าน | สถานะ แผน และผลคำนวณอิสระ |
| บทสนทนาต่อเนื่อง | Offline 60/60 เทิร์นผ่าน | Routing, บริบท, ถามกลับ, การแสดงผลและตัวเลข |
| Groq integration | Router/Planner และ Live HTTP smoke 3 เทิร์นผ่าน | ตรวจการเชื่อมต่อ ไม่ใช่ความแม่นทั่วไปของโมเดล |
| Frontend | TypeScript และ Docker production build ผ่าน | ตรวจ build ไม่ใช่ผล load test หรือการรับรอง accessibility |

ผลเปรียบเทียบ Gemini วันที่ **11 ตุลาคม** เก็บแยกเป็นหลักฐานย้อนหลัง: development 10 และ held-out 14 เทิร์น เทียบสามวิธี Hybrid ผ่าน 14/14 แต่ไม่ได้เรียก LLM ใน split นี้ ส่วน LLM-only ผ่าน 6/14 ตาม rubric แบบเข้มงวด ผลเหล่านี้ไม่ครอบคลุม router รุ่นใหม่และไม่ใช่ผลประเมิน Groq ปัญหาบัญชี provider เก็บไว้ในหลักฐานตามวันที่ ไม่ใช้เป็นคำอธิบายความสามารถถาวรของระบบ

อ่าน [สถานะการตรวจ](docs/verification.md), [วิธีประเมิน](docs/llm-evaluation.md), และ [ผลเต็มที่เก็บข้อผิดพลาดไว้](docs/evidence/llm/results.md)

## ขอบเขตและข้อจำกัด

- **การตั้งค่าระบบ:** Compose ที่จัดเตรียมไว้เปิดบริการเฉพาะเครื่องและใช้ credentials สำหรับพัฒนา การเปิดให้หลายผู้ใช้ต้องเพิ่มระบบยืนยันตัวตน สิทธิ์เข้าถึงบทสนทนา การจำกัดคำขอ การจัดการ secrets และนโยบายเก็บรักษาข้อมูล ซึ่งยังไม่รวมในการตั้งค่าปัจจุบัน
- ยอดสินเชื่อ/เงินฝากเป็น stock ณ สิ้นงวด รวมจังหวัดภายในเดือนเดียวได้ แต่ห้ามบวกข้ามเดือน ตัวชี้วัดต่อคนไม่ใช่หนี้ส่วนบุคคล และจำนวนสาขาไม่ใช่ financial access ทั้งหมด
- กรุงเทพฯ อาจได้รับผลจากการบันทึกสำนักงานใหญ่ ประชากรทะเบียนไม่ใช่จำนวนลูกค้า GPP กับยอดธนาคารต่างปี และความสัมพันธ์ไม่ยืนยันเหตุและผล
- World Bank vintage ที่ตรวจคือ 8 ต.ค. 2569 อยู่หลังงวดธนาคารทั้งหมดใน snapshot จึงแสดงเงินเฟ้อย้อนหลังเป็น unavailable ตามกฎ conservative availability ไม่เติมศูนย์หรือสร้างวันเผยแพร่ย้อนหลัง
- ข้อมูลย้อนหลัง 25 เดือนไม่พิสูจน์ว่า Airflow รันต่อเนื่องหนึ่งเดือน ต้องตรวจ scheduled run history จริงแยกกัน
- คำถามและบริบทอาจถูกส่งไปผู้ให้บริการ LLM; checkpoints เก็บประวัติ การเริ่มใหม่ไม่ลบ session เก่า ห้ามใส่ข้อมูลลูกค้าหรือ secrets

เอกสารหลักใช้ภาษาอังกฤษ โดยเก็บตัวอย่างคำถามและผลจังหวัดภาษาไทยตามแอป ดู [สารบัญ](docs/README.md), [roadmap](PROJECT_PLAN.md) และ [แนวทาง contribution](CONTRIBUTING.md)
